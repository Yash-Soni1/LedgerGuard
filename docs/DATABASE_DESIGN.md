# LedgerGuard - Database Design

## 1. Introduction

LedgerGuard uses MongoDB as its primary database, with Mongoose as its Object Data Modeling (ODM) library.

The database architecture is designed to support:

- Multi-tenant data isolation.
- Organization and user management.
- Usage event tracking.
- Idempotent billing operations.
- Financial ledger records.
- Historical analytics.

**Current implementation:** MongoDB Atlas connectivity has been verified. User, Organization, and OrganizationMembership models have been implemented. The dynamic tenant database architecture and billing-related models remain under development.

## 4. Implemented and Planned Data Models

### 4.1 User — Implemented

Stores user account information.

| Field | Purpose |
|---|---|
| `_id` | Unique user identifier |
| `name` | User's display name |
| `email` | Unique account email |
| `passwordHash` | Securely hashed password |
| `createdAt` | Account creation time |
| `updatedAt` | Last update time |

**Implementation details:**

- Passwords are hashed using bcrypt with 12 salt rounds.
- Email addresses are normalized.
- Password hashes are excluded from default queries.
- Email uniqueness is enforced through a unique index.

Model location:

```text
backend/src/models/User.ts
```

### 4.2 Organization — Implemented

Represents a tenant or organization.

| Field | Purpose |
|---|---|
| `_id` | Organization identifier |
| `name` | Organization name |
| `slug` | Unique organization identifier |
| `status` | Organization status (`active` or `suspended`) |
| `createdBy` | Reference to the user who created the organization |
| `createdAt` | Creation timestamp |
| `updatedAt` | Last update timestamp |

**Implementation details:**

- Organization slugs are unique.
- Slugs are stored in lowercase.
- Organization status defaults to `active`.
- The creator is referenced through the `User` model.

Model location:

```text
backend/src/models/Organization.ts
```

### 4.3 OrganizationMembership — Implemented

Connects users to organizations and defines their organization-level roles.

| Field | Purpose |
|---|---|
| `_id` | Membership identifier |
| `userId` | Reference to a user |
| `organizationId` | Reference to an organization |
| `role` | Organization-level role |
| `createdAt` | Membership creation time |
| `updatedAt` | Last update time |

Supported roles:

- `owner`
- `admin`
- `member`

**Implementation details:**

- A user can belong to multiple organizations.
- Each membership connects one user to one organization.
- A unique compound index on `userId` and `organizationId` prevents duplicate memberships.
- The organization creator automatically receives the `owner` role.

Model location:

```text
backend/src/models/OrganizationMembership.ts
```

## 5. Multi-Tenant Database Strategy

LedgerGuard plans to implement dynamic tenant-specific database connections.

The connection registry will:

1. Resolve an authorized tenant.
2. Identify its configured database.
3. Reuse an existing connection when available.
4. Create a connection when necessary.
5. Manage connection lifecycle and failures.
6. Prevent unauthorized cross-tenant access.

Tenant database selection must be controlled by trusted server-side configuration, not arbitrary client input.

**Current status:** Organization-level membership authorization has been implemented and tested. Dynamic tenant-specific database routing is still planned.

## 7. Transaction Strategy

MongoDB multi-document transactions are used for operations that require atomic consistency.

**Implemented transaction: Organization creation**

The organization creation service performs the following operations within a MongoDB transaction:

1. Creates the organization.
2. Creates an owner membership for the authenticated user.

Both operations succeed or fail together.

MongoDB Atlas transaction support has been verified through successful organization creation.

**Planned transaction use:**

A future billing operation may involve:

1. Recording a usage event.
2. Creating corresponding ledger entries.
3. Updating derived account information.

These operations must succeed or fail together.

**Important:** MongoDB multi-document transactions require a replica set or sharded cluster.

---

## 8. Data Integrity Principles

- Use schema validation.
- Enforce unique database indexes.
- Validate tenant ownership.
- Use atomic database operations where appropriate.
- Use transactions for multi-document financial operations.
- Avoid exposing internal database identifiers to unauthorized clients.
- Preserve an auditable ledger history.
- Derive organization access from verified authentication and membership.
