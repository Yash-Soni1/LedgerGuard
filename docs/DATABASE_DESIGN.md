# LedgerGuard - Database Design

## 1. Introduction

LedgerGuard uses MongoDB as its primary database, with Mongoose as its Object Data Modeling (ODM) library.

The database architecture is designed to support:

- Multi-tenant data isolation.
- Organization and user management.
- Usage event tracking.
- Idempotent billing operations.
- Financial ledger records.
- Historical analytics.

**Current implementation:** MongoDB Atlas connectivity has been verified. Application schemas and the complete tenant database architecture are planned.

## 4. Planned Data Models

The following models represent the intended application design. They have not yet been implemented.

### User

Stores user account information.

Potential fields:

| Field | Purpose |
|---|---|
| `_id` | Unique user identifier |
| `name` | User's display name |
| `email` | Unique account email |
| `passwordHash` | Securely hashed password |
| `createdAt` | Account creation time |
| `updatedAt` | Last update time |

### Organization

Represents a tenant or organization.

Potential fields:

| Field | Purpose |
|---|---|
| `_id` | Organization identifier |
| `name` | Organization name |
| `slug` | Unique organization identifier |
| `databaseIdentifier` | Internal tenant database reference |
| `createdAt` | Creation timestamp |

### Membership

Connects users to organizations.

Potential fields:

| Field | Purpose |
|---|---|
| `_id` | Membership identifier |
| `userId` | Reference to a user |
| `organizationId` | Reference to an organization |
| `role` | Organization-level role |
| `createdAt` | Membership creation time |

### UsageEvent

Records usage generated by an organization.

Potential fields:

| Field | Purpose |
|---|---|
| `_id` | Event identifier |
| `eventId` | Unique idempotency identifier |
| `organizationId` | Tenant reference |
| `eventType` | Usage category |
| `quantity` | Recorded usage amount |
| `metadata` | Additional event information |
| `createdAt` | Event timestamp |

### LedgerEntry

Records financial changes.

Potential fields:

| Field | Purpose |
|---|---|
| `_id` | Ledger entry identifier |
| `organizationId` | Tenant reference |
| `eventId` | Associated usage event |
| `entryType` | Debit or credit |
| `amount` | Financial amount |
| `currency` | Currency code |
| `reference` | Transaction reference |
| `createdAt` | Entry timestamp |

These are conceptual field proposals. Final schemas, validation rules, and relationships will be determined during implementation.

## 5. Multi-Tenant Database Strategy

LedgerGuard plans to implement dynamic tenant-specific database connections.

The connection registry will:

1. Resolve an authorized tenant.
2. Identify its configured database.
3. Reuse an existing connection when available.
4. Create a connection when necessary.
5. Manage connection lifecycle and failures.
6. Prevent unauthorized cross-tenant access.

Tenant database selection must be controlled by trusted server-side configuration, not arbitrary client input.

---

## 6. Indexing Strategy

Planned indexes include:

| Collection | Index | Purpose |
|---|---|---|
| Users | Email | Unique account lookup |
| Organizations | Slug | Unique organization lookup |
| Memberships | User + Organization | Prevent duplicate membership |
| Usage Events | Event ID + Tenant | Durable idempotency |
| Ledger Entries | Event ID + Tenant | Prevent duplicate ledger operations |

Final index definitions will be documented alongside the actual Mongoose schemas.

---

## 7. Transaction Strategy

MongoDB multi-document transactions will be used for operations that require atomic consistency.

For example, a billing operation may involve:

1. Recording a usage event.
2. Creating corresponding ledger entries.
3. Updating derived account information.

These operations must succeed or fail together.

**Important:** MongoDB multi-document transactions require a replica set or sharded cluster. The current Atlas deployment must be verified for transaction support before implementation.

---

## 8. Data Integrity Principles

- Use schema validation.
- Enforce unique database indexes.
- Validate tenant ownership.
- Use atomic database operations where appropriate.
- Use transactions for multi-document financial operations.
- Avoid exposing internal database identifiers to unauthorized clients.
- Preserve an auditable ledger history.
